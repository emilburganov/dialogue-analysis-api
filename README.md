# Сервис для анализа диалогов — API

API для внутреннего сервиса анализа диалогов менеджеров с клиентами.

## Требования

- [Docker Desktop](https://www.docker.com/products/docker-desktop/)

## Запуск

```bash
docker compose up -d --build
```

При первом запуске автоматически:
- создаётся `.env` из `.env.example`, если не было файла `.env`
- устанавливаются зависимости Composer
- выполняются миграции и сиды

Тестовые пользователи (пароль: `password`):
- `admin@example.com` — администратор, видит все диалоги
- `anna@example.com` — менеджер, видит только свои диалоги
- `igor@example.com` — клиент, видит только свои диалоги

## API

| Метод | URL | Описание |
|-------|-----|----------|
| POST | `/api/login` | Авторизация |
| GET | `/api/me` | Текущий пользователь |
| POST | `/api/logout` | Выход |
| GET | `/api/dialogues` | Список диалогов |
| GET | `/api/dialogues/{id}` | Диалог с сообщениями |
| GET | `/api/dialogues/{id}/analysis` | Анализ диалога (менеджер, админ) |
| GET | `/api/analysis-rules` | Список правил анализа (админ) |
| GET | `/api/analysis-rules/types` | Доступные типы правил (админ) |
| POST | `/api/analysis-rules` | Создать правило (админ) |
| PUT | `/api/analysis-rules/{id}` | Обновить правило (админ) |
| PATCH | `/api/analysis-rules/{id}/toggle` | Включить/выключить правило (админ) |

Заголовок: `Authorization: Bearer {token}`

## Анализ диалогов

Система автоматически проверяет переписку по набору правил и возвращает список событий с критичностью, описанием и ссылками на сообщения.

### Реализованные правила

| Правило | Критичность | На что реагирует |
|---------|-------------|---------------|
| `slow_response` | medium | Менеджер ответил позже 30 минут |
| `client_silence` | high | Последнее сообщение в диалоге от менеджера |
| `unanswered_client` | high | Клиент ждёт ответа |
| `objection_detected` | low | Ключевые фразы возражений |
| `client_escalation` | medium | 3+ сообщения клиента подряд |

### Архитектура

Сервисы разделены по доменам:

| Домен | Namespace | Ответственность |
|-------|-----------|-----------------|
| Auth | `App\Services\Auth` | Авторизация, роли |
| Dialogue | `App\Services\Dialogue` | CRUD диалогов, сообщения |
| Analysis | `App\Services\Analysis` | Правила анализа, движок проверки, события |

Между **Dialogue** и **Analysis** — Anti-Corruption Layer:
- Analysis объявляет порт `DialogueReaderInterface` и свои типы (`DialogueSnapshot`, `MessageSnapshot`, `MessageAuthor`).
- Адаптер `Dialogue\Integration\ForAnalysis\DialogueReaderAdapter` переводит модели Dialogue в снимки для Analysis.
- Сервисы не импортируют классы друг друга напрямую.

- Справочник типов правил в таблице `analysis_rule_types` (slug, название, схема параметров, класс-исполнитель)
- Экземпляры правил в таблице `analysis_rules` (slug, тип, параметры, критичность, флаг `is_enabled`)
- `AnalysisRuleRegistry::types()` загружает типы из БД; классы-исполнители хранятся в `executor_class`
- Экземпляры правил хранятся в БД: можно включать/выключать, менять параметры и добавлять новые варианты одного типа без правок основного кода
- Каждый тип — отдельный класс, реализующий `AnalysisRuleInterface` (`App\Services\Analysis`)
- `AnalysisService` загружает включённые правила из БД, запускает их и сохраняет события в `dialogue_analysis_events`
- Доступ к анализу — у менеджера (свои диалоги) и администратора; управление правилами — только у администратора

### Управление правилами (SPA)

Администратор может открыть раздел **«Правила анализа»** (`/analysis-rules`):

- просмотр всех правил;
- редактирование, включение/выключение и удаление только **пользовательских** правил;
- системные правила доступны только для просмотра;
- добавление нового экземпляра существующего типа. Например, второе правило «долгий ответ» с другим порогом.

Новый **тип** правила требует класса-исполнителя в коде и записи в `analysis_rule_types` (через сид или админку), но настройка и включение экземпляров полностью управляются через интерфейс.
